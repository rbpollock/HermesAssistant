# Part A — The five flow bugs (already diagnosed, approved)

These were identified and verified in the previous session. They are the "not fluid" core. Implement FIRST — they're small and independent.

## A1. Wake word speaks back (biggest fix)

**Problem:** `HermesForegroundService.sendDictatedTextHttp()` POSTs the phrase to `/chat/message`, gets Hermes' reply text, then **throws it away** — only `injected_live` is read, notification says "Message sent". The reply is never spoken, never in history. Wake word = one-way conversation.

**Fix:**
- Parse `reply` from the JSON response in `sendDictatedTextHttp()`.
- Append `ChatMessage("hermes", reply)` to shared `chat_history.json` (via `ChatHistoryStore`).
- Broadcast `ACTION_DICTATION_RESULT`-style "reply ready" event so MainActivity (if alive) shows it; ALSO queue the reply for TTS playback through `AudioPlayer.speakAlert`-equivalent so it's audible.
- Keep the `injected_live` check → green check + "Delivered to live session" behavior.

**Files:** `app/src/main/java/com/example/hermesassistant/HermesForegroundService.kt` (sendDictatedTextHttp), possibly a small helper in `ChatHistoryStore`.

**Verification:** wake word → speak → hear Hermes' spoken reply; history shows the hermes bubble.

## A2. Progressive audio (stop the long silent wait)

**Problem:** server streams MP3 chunks as generated, but the app buffers ALL chunks to a temp file and only plays at `audio_end`. Long response = 10–30s silence after "Thinking...".

**Fix options (pick one at implementation time):**
- **Option 1 (preferred):** Start `MediaPlayer` on the temp file as soon as the first bytes arrive, using `prepareAsync()` + `setDataSource(fd)` with a seekable local file, and let it play while the file grows. Risk: MediaPlayer may read-ahead beyond written data → garbled tail.
- **Option 2 (safe):** Server sends `audio_start` + periodic `audio_segment` markers; app plays each completed segment via a small queue (same FIFO as AudioPlayer). More server churn but deterministic.
- **Option 3 (minimum viable):** Keep buffering but add a "Generating response…" status heartbeat so at least the UI doesn't look frozen, then play at audio_end as today.

**Files:** `app/src/main/java/com/example/hermesassistant/MainActivity.kt` (onAudioBytes/onAudioEnd), `streaming_backend/server.py` (only for Option 2), `app/src/main/java/com/example/hermesassistant/AudioPlayer.kt`.

**Decision needed:** Option 1 is a small client change but has read-ahead risk; Option 2 is robust but touches the server. **Default to Option 1 with a verification test; fall back to Option 2 if audio glitches.**

## A3. One chime per transition (kill the double-chime jank)

**Problem:** `onEndOfSpeech` → `onStoppedListening()` (stop chime) then `onResults` → `onStoppedListening()` again (stop chime #2). Errors double-fire too. Every phrase = stacked stop chimes.

**Fix:** Make the stop chime fire exactly once per listening session:
- In `VoiceInput`, add a `chimeFired` guard: `onStoppedListening()` only notifies the listener the FIRST time the state leaves LISTENING (i.e., guard inside `VoiceInput` so callers can't double-fire).
- Alternatively: MainActivity dedupes — only play stop chime on transition `LISTENING → IDLE`, never on `THINKING`-ish intermediate callbacks.

**Files:** `app/src/main/java/com/example/hermesassistant/VoiceInput.kt`, `app/src/main/java/com/example/hermesassistant/MainActivity.kt` (wireVoice).

**Verification:** speak one phrase → exactly one stop chime.

## A4. Auto-listen policy (stop chime-chime-chime at idle)

**Problem:** after ANY response, `scheduleAutoListen` waits 700ms, plays START chime, begins listening; if nobody speaks, timeout plays ANOTHER stop chime. The phone chimes even when you're just reading.

**Fix:**
- Only auto-listen after a turn **the user initiated** (track `lastTurnUserInitiated` in MainActivity, set true in `sendUserMessage` from voice/button, false for notify-only activity).
- Longer quiet delay before auto-listen (700ms → 2500–3000ms).
- If the last interaction was a **notify** (someone else's session finished), do NOT auto-listen — just return to wake-word idle.

**Files:** `app/src/main/java/com/example/hermesassistant/MainActivity.kt` (scheduleAutoListen + callers).

**Verification:** after a reply you initiated → gentle re-listen; after a background notify → silence, just the wake word.

## A5. Unify the reply path

**Problem:** WS replies (button/text) stream audio + update history; HTTP replies (wake word) do neither. Two divergent experiences for the same "ask Hermes".

**Fix:** One method, e.g. `handleAssistantReply(text: String, sessionId: String, audioFile: File?)` in MainActivity that does: history append → render → chime/status → enqueue playback. WS `onTextResponse` and the wake-word HTTP path (A1) both call it.

**Files:** `app/src/main/java/com/example/hermesassistant/MainActivity.kt`, `app/src/main/java/com/example/hermesassistant/HermesForegroundService.kt`.

# Part B — Half-window as a real listening frontend

**Design intent (user's words):** the bottom half-window should do immediate listening and act as a smaller frontend to the main activity (fullscreen chat). Right now it's a big ring + status + one button; it doesn't *feel* like a frontend and the fullscreen/panel relationship is muddled.

## B1. Half-window = the always-listening surface

**Proposal:**
- When the assistant panel is visible (bottom half), it ALWAYS shows live listening state (ring animates, status = "Listening…", button = "TAP TO CANCEL").
- Opening the app (or any activation) puts the app in this half-window state first, listening immediately (already true via `beginListening` in onCreate — keep, make it visually obvious).
- The half-window is compact: smaller ring (~120dp not 180dp), status + subtext + button, no chrome that isn't listening-related.
- Tapping the panel/button area while idle = start listening; while listening = cancel.

**Files:** `app/src/main/res/layout/activity_main.xml` (assistantPanel block), `app/src/main/java/com/example/hermesassistant/MainActivity.kt`.

## B2. Collapse/expand — the full audit

**Current problems (verified):**
1. The collapse/expand band (`panelCollapseBar`) is 52dp between chat and panel; behavior changes with state, and there have been multiple "can't find it / it's not there / move it up" complaints (v1.6.28–v1.6.34). It's confusing.
2. When collapsed, `assistantPanel` is `GONE` — there is **no listening surface at all**; the only control is the band at the bottom. The half-window frontend disappears exactly when you might want it.
3. `applyPanelCollapsed` adds 5% bottom padding to chatSection when collapsed (band floats) — this was a user-directed tweak; keep but make it consistent with the new design.
4. Nav-bar inset handling is ad-hoc (`updateNavBarInset`, `ViewCompatRootInsets`, `onWindowFocusChanged`).

**Proposal — three explicit states, no hidden traps:**
- **EXPANDED (default):** chat top 45–50%, band, listening panel bottom 50–55%. Band label "Collapse panel" + down chevron.
- **COLLAPSED:** chat fullscreen; a **slim listening strip** (~64dp) pinned at the bottom ABOVE the nav bar replaces the old bare band. The strip contains: small status dot/ring, one-line status, and a compact speak/cancel button — i.e., the half-window frontend survives in miniature. Tapping the strip's chevron returns to EXPANDED.
- **FULLSCREEN (keyboard):** when the typing row is open, chat + input fill the screen and the strip hides until the keyboard closes (auto-return to previous state).

**Files:** `app/src/main/res/layout/activity_main.xml` (rework panelCollapseBar into a real strip layout), `app/src/main/java/com/example/hermesassistant/MainActivity.kt` (applyPanelCollapsed + updateNavBarInset), possibly a new small drawable for the strip.

**Open question for user:** should the collapsed strip auto-listen (hands-free) or just show status? **Default: status + tap-to-listen** (less surprising).

## B3. Keyboard appearance & the typing row

**Current problems (verified):**
1. `windowSoftInputMode="adjustResize"` + typing row inside chatSection: opening the keyboard resizes the whole activity, so the listening panel gets crushed behind the keyboard and the expand/collapse band + panel fight for space.
2. The keyboard icon (`typeToggleButton`) lives in the assistant panel top-right; it toggles `textInputRow` AND shows/hides the IME manually. Focus/IME state isn't persisted across panel toggles.
3. The typing row is `visibility="gone"` by default; there's no visual affordance that text input exists when the panel is collapsed.

**Proposal:**
- Give the activity a stable `android:windowSoftInputMode="adjustResize"` (keep) but make the typing row the **bottom element of chatSection** (already true) and ensure the panel is never compressed: when the typing row is visible, collapse the listening panel automatically (or hide just the panel, keep the strip) so the keyboard + input + chat use the full screen.
- Move the keyboard toggle into the **collapsed strip** as well, so typing is reachable from both states.
- Persist the typing-row visibility in a field (not just view visibility) and restore it after panel toggles.
- On send: clear input, hide keyboard ONLY if the user's last action was send (not if they're composing multi-line).

**Files:** `app/src/main/java/com/example/hermesassistant/MainActivity.kt` (wireTextInput, typeToggleButton handler), `activity_main.xml`.

## B4. Session chips — centering, legibility, mute/forget/clear

**Current problems (verified):**
1. Chips are 12sp with a colored 1dp border; long titles truncate without ellipsis context; selected chip = solid fill + dark text (ok) but unselected chips are dim.
2. Chips row is a HorizontalScrollView with fixed 48dp height; there is NO way to manage sessions: no mute (stop notifies from a session), no forget (remove from list), no clear-all.
3. Chip centering: `sessionChipsRow` has `wrap_content` width inside the scroll view, gravity center_vertical — fine horizontally, but the row doesn't center within the screen when content is short (it left-aligns). Minor.
4. `SessionStore` already stores `host` + `lastSeen` but the UI never shows them.

**Proposal:**
- **Chips:** bump to 13sp, add `maxLines=1` + `ellipsize=end`, show host as a small second line or superscript when present (e.g., "Solar Trivia · server"). Keep the 10-color palette. Selected = solid color + dark text (current); unselected = border + light text (current). Add a subtle "·" separator between chip and a trailing manage button.
- **Mute:** add `muted: Boolean = false` to `KnownSession` (persisted in sessions.json). In `MainActivity.handleNotify`, skip `showSystemNotification` + TTS for muted sessions (still show in history as a dim row). Long-press a chip → small menu (Mute/Unmute, Forget, Clear all).
- **Forget:** `SessionStore.remove(id)` — removes from chip list (history stays; it's the same session id in chat_history.json).
- **Clear:** chips row gets a trailing "×" / overflow (⋮) button → Confirm dialog → `SessionStore.clear()` + optionally `ChatHistoryStore.clearHistory()`.
- **Centering:** when few chips, center the row content in the available width (use a `FrameLayout` wrapper or set `sessionChipsRow.gravity` / measure). Keep left-align when overflowing.

**Files:** `app/src/main/java/com/example/hermesassistant/SessionStore.kt` (muted field, remove()), `MainActivity.kt` (renderSessionChips, long-press, handleNotify mute check), `activity_main.xml` (chip row wrapper, overflow button), possibly `strings.xml` for menu labels.

**Open question for user:** should "Forget" also remove that session's history bubbles, or just the chip? **Default: chip only** (non-destructive).

# Risks / tradeoffs

- **A2 progressive audio (Option 1)** — MediaPlayer read-ahead past written data can garble the tail. Mitigation: write-ahead pad, test with a 60s+ response, fall back to Option 2.
- **B2 strip rework** — biggest layout change; touch targets on a 64dp strip must stay ≥48dp. Keep the strip simple.
- **B4 mute** — muting must NOT drop real events (user preference: dedupe without dropping). Muted sessions still appear in history; only the notification/TTS is suppressed.
- **Keyboard fights panel** — auto-collapsing the panel when typing is the least-surprising behavior; verify focus doesn't bounce.
- No new components anywhere (user constraint) — all changes are inside MainActivity/service/store/layouts.
